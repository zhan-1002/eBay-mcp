## 二、缺陷清单

### P0-1 凭据缺失，两个通道都进不去

- 位置：`config_load.py:18-41`；期望文件 `紫鸟ebay\config.local.json`（由 `config.example.json` 复制）
- 现象：实测 `ziniao_creds()` 抛 `RuntimeError: 缺少紫鸟账号`；`ebay_api_creds()` 抛 `缺少 eBay API 密钥`。
- 说明：**这是设计如此，不是 bug**（凭据不落脚本是对的）。但它让"真机跑 120 条"这一步目前无法启动。
- 处理：用户自己填 `config.local.json`，**不要把密码发到对话里**。或设环境变量 `ZINIAO_COMPANY / ZINIAO_USERNAME / ZINIAO_PASSWORD`（`config_load.py:21-23`）。

### P0-2 配送地设置：会失败但永远报成功

- 位置：`collect_ziniao.py:65-140`（`set_ship_to`）
- 三个独立问题：
  1. `collect_ziniao.py:95-98`：`combo = page.locator("select, [role='combobox']").first` 后直接 `combo.select_option(label=...)`，**没有 `.count()` 判断**。弹层里若没有原生 `select`，这一步抛异常 → 被 `except: pass` 吞掉，没有任何日志。
  2. `collect_ziniao.py:93-110` 三段 `try/break`：第一段失败后 **`break` 不在 except 里**，而是在 try 末尾（`collect_ziniao.py:99`）—— 只要 `combo.count() > 0` 且 `select_option` 不抛异常就跳出，后续两种兜底（`get_by_label`、`get_by_text`）永不执行；反之第一段抛异常则直接进第二段。逻辑与注释意图不完全一致。
  3. `collect_ziniao.py:140`：`return True` 是无条件的。**即使上面一个元素都没点到，也返回成功**，`collect_ziniao.py:139` 的日志同样无条件打印。于是"配送弹层已点"是假信号。
- 影响：需求里被反复强调的一条（「要按站点选择配送位置，如果按IP来会都去到香港」）目前**没有任何可信的验证信号**。
- 兜底：`sites.py:99-106` 的 `search_url()` 带了 `_stpos=<zip>&_fcid=<country_id>`，能在 URL 层顶一部分。注意 `sites.py` 的邮编与《市场调研.xlsx》不一致（见 P3-3）。
- 处理建议：`set_ship_to` 必须返回"实际生效与否"，并把结果打出来；失败时至少明确提示"已退化到 URL 参数兜底"，而不是谎报成功。

### P0-3 列表页选择器是"一套写法"，未实测

- 位置：`collect_ziniao.py:161`（`page.locator("li.s-item")`）、`:170`（`.s-item__title`）、`:181`（`.s-item__price`）、`:192`（`a.s-item__link`）、`:199`（`.s-item__subtitle, .s-item__condition`）
- 风险：eBay 近年大量改用 `li.s-card` + `.s-card__title / .s-card__price`。一旦命中新结构，`items.count()` 直接是 0。
- 失败表现：`collect_on_page` 打印「本页有效 0 条」→ 外层 `break` → 最终「未采集到数据」，退出码 1（`run_keyword_research.py:200-203`）。**没有任何测试能拦住这个**（采集段 0 单测）。
- 处理建议：改成 `li.s-item, li.s-card` 多选择器 + 字段级多选择器兜底，并在启动时打印"命中条数"，让零结果一眼可见。

### P0-4 集 120 条的循环有逻辑缺口

- 位置：`collect_ziniao.py:281-296`
- 现象：`parse_listing_page(page, start_pos=len(items)+1, need=max_items-len(items))`，而 `parse_listing_page:164-166` 是 `for i in range(count)` + `if len(results) >= need: break`。
  - 第 1 页 `_ipg=240`、`need=120` → 一次收满 120 条；
  - `page_no=2` 时 `need=0` → 首轮 `break`，返回空 → `collect_ziniao.py:293-294` 判定"本页无结果"收工。
- 结论：**恰好能拿到 120 条，但靠的是巧合**（首页默认 ≥120 条）。若目标站点结果不足 240、或改 `--max`，行为就不对了。`need<=0` 时应直接跳出循环，而不是当作"没有结果"。
- 另：`page_no <= 4` 的硬上限（`collect_ziniao.py:281`）和 `_ipg=240` 组合，实际上第 2-4 页永远拿不到数据。

### P1-1 广告位判定不可信

- 位置：`collect_ziniao.py:143-157`（`_is_sponsored`）
- 现象：第二段把 `item.inner_text() + item.inner_html()` 拼起来，只要含 `sponsored / advertisement / anzeige / annonce / anuncio / 推广 / 广告` 就判为广告位。**扫了整个 item 的 HTML**，页面/卡片模板里出现这些词就误判。
- 影响：`analyze.py:363` 的 `ad_count`、Excel `总览` 里的「广告条数」会虚高；需求第 6 条「是否为广告位」的取数因此不可信。
- 处理建议：只认卡片上的广告标签元素（显式徽标/`etrs` 类），不扫 HTML 全文。

### P1-2 末级类目 ID 实际取不到

- 位置：`collect_ziniao.py:36-45`（`EXTRACT_JS` 取类目段）、`:33`（面包屑正则）
- 问题：
  1. 主路径 `html.match(/"categoryId"\s*:\s*"(\d+)"/)` 依赖页面内嵌 JSON 里恰好有 `"categoryId":"数字"` 这种形态；eBay 商品页更常见的是 URL 参数 `_sacat=` / 面包屑链接，该正则与真实键名对不上。
  2. DOM 兜底 `crumbs` 走 `/b/[^/]+/(\d+)`、`_sacat=(\d+)`、`/sch/(\d+)`。新版商品页的面包屑通常**不带数字 ID**，所以 `crumbIds` 常为空。
  3. 结果 `primaryCategoryId` 为空 → `collect_ziniao.py:246-260` 里 `leaf=[]`、`has_secondary_category=False`。
- 影响：需求第 10、11 条（「获取上架类目以及类目ID，最重要的是末级类目ID」「单个SKU可以属于两个类目，第二个类别要收费」）**整条链给不出结果**；Excel 的 `主类目` / `第二类目` 两个 sheet 会是空的。
- 另外：紫鸟路径的 `dominant_category_id` 恒为 `""`（`collect_ziniao.py:303`），`run_keyword_research.py:212-213` 那段兜底等于死代码。
- 处理建议：优先从商品页 URL 的 `_sacat` / 页面里的类目链接取，并且**必须在真机上 dump 一次真实 DOM 再定正则**——不要再猜。

### P1-3 「最近成交」这条需求完全没实现

- 出处：`eBay新需求20260813.xlsx` 最后一条「左侧"show only"选"sold item"，可以看到最近售出的链接，按前面再抓一遍，分别分析最近成交的是什么链接」。
- 现状：`紫鸟ebay` 工程**没有任何 sold 采集**（无参数、无解析、无输出列）。旧版 `ebay_zc\ziniao_ebay_search.py:779` 有个 `--sold`，但它只是把 `LH_Sold=1&LH_Complete=1` 加进 URL 后用**同一套** `li.s-item` 解析器再抓一遍普通字段，sold 页的成交日期/成交价拿不到。
- 处理建议：sold 页单独一个解析器（标题、成交价、成交日期、链接），输出单独 sheet（如 `最近成交`），并和主列表区分开。

### P1-4 推荐 title 机械拼接，且品牌名放首位

- 位置：`analyze.py:264-333`（`generate_titles`）
- 现象：
  1. 模板 `[brand, kw, type_name, color, material]`（`analyze.py:290`）把**竞品品牌名放在首位**。实测产物第一条就是 `Sony wireless headphones Over-Ear Black`。这是从竞品标题里抄来的品牌词，直接拿去上架有侵权风险。
  2. 凑数逻辑 `analyze.py:327-332` 用 `"Lot%s" % i` 填充，产出 `... Lot1/Lot2/Lot3` 这类无意义标题。
  3. `top_tokens` 直接拼进标题（`analyze.py:295-303`），产出的多条只是同一个词袋的不同排列，语义重复度高（实测 20 条里大量同义）。
- 处理建议：品牌词进黑名单剔除；去掉 `Lot` 凑数；标题模板排优先级 + 后缀去重（避免同词不同序）。

### P1-5 `has_secondary_category` 采了但没用

### P1-6 变体价格区间被取成最小值

- 位置：`collect_ziniao.py:184`（`re.search(r"([A-Z]{3})?\s*([\d.,]+)", price_display)`）、`:187`（`float(...replace(",",""))`）
- 现象：eBay 卡片常见 `US $10.99 to $19.99` 或 `$10.99 - $19.99`。上面正则会命中第一个数字 → **只取到区间下限**，`price_display` 里保留全文但 `price` 是错的。
- 影响：需求第 12、13 条明确「SPU当作SKU来抓价格区就行」「SPU价格段分析」——价格段分析（`analyze.py:153-199`）直接建立在这个数字上，会系统性偏低。
- 同类问题：`ebay_zc\ziniao_ebay_search.py:299-307` 的 `_parse_price` 把 `,` 一律删掉，德/法/西的 `12,99 €` 会变成 `1299`（放大 100 倍）。
- 处理建议：区间取 min~max 两个数（或按需求存"区间"两列），并保留原币种文本。
